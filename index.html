GIT 版控作業指南

把需求、維運問題與 IT 提供的程式碼，分別放在可追溯的工作分支；經過 SIT 整合驗證後，再由同一批工作分支個別納入 UAT 包版。

Branch StrategyPR / Code ReviewSIT / UATPROD Record
一句話原則SIT 與 UAT 都是整合目標；來源永遠是各自的工作分支。SIT 不是交付基準，UAT 才是包版、差異檔與交付基準。

為什麼 SIT、UAT 都採個別工作分支 merge？

因為每一條 feature/、issue/、sync/ 都代表一個可以獨立追蹤、驗證與交付的變更單位。SIT 負責整合與驗證，UAT 負責包版與交付；兩個環境雖然都是整合目標，但不代表要把整個 SIT 一次搬到 UAT。

可追溯

每個需求、Issue 或 IT 調整都有自己的 branch、PR 與 merge 紀錄，能清楚知道哪一項變更進入哪個環境。

風險隔離

某一條工作分支在 SIT 發生問題時，可以單獨修正、暫緩或回退，不會把其他已驗證內容一起影響。

精準交付

UAT 只納入已通過 SIT 驗證且本次要交付的工作分支，包版、差異檔與交付清單才會一致。

2. Branch 清單與角色定義

本專案的 branch 可分成「開發基線」、「工作分支」與「環境整合 / 交付」三類。sync/ 與 feature/、issue/ 的流程定位相同，差異只在程式碼提供者是 IT。

dev

開發基線

當 main 更新時，將 main merge 到 dev，作為新一輪工作分支的起點。

feature/ · issue/ · sync/

獨立工作分支

三者都可個別進入 SIT、UAT；差別是來源目的與製作者不同。

SIT · UAT · main

環境與交付分支

SIT 做內部驗證，UAT 做包版交付，main 留存已確認 PROD 上線紀錄。

3. 標準流轉與不可混用的邊界

從 dev 建立工作分支

依情境建立 feature/<需求>、issue/<編號> 或 sync/<日期>。

工作分支完成開發 / 程式提供

完成必要檢查與 commit，push 到遠端；三類工作分支都可獨立建立 PR 或進行 merge。

個別 merge 進 SIT

每個 feature、issue、sync 分支分別進入 SIT，不把多個來源壓成一個模糊版本。

SIT 驗證

進行 Code Review、內部整合、自測與環境驗證；若失敗，回原工作分支修正。

個別 merge 進 UAT

驗證通過的各工作分支，再分別 merge 進 UAT；不採用 SIT → UAT 整批 merge。

IT 上線後回併 main

包版、差異檔與交付以 UAT 為準；正式環境確認後，將本次已交付內容收斂回 main。

最重要的更正請把「來源 branch」記在每一次 SIT / UAT merge 的紀錄中。SIT 與 UAT 都是目標分支，不是下一階段的唯一來源分支。

4. 工作分支：feature / issue / sync

4.1 Feature：新合約需求

假設需求代號為 REQ-202608-001：

git switch dev
git pull origin dev
git switch -c feature/REQ-202608-001
git add <變更檔案>
git commit -m "[DEV][帳單功能][REQ] 新增合約需求 REQ-202608-001"
git push -u origin feature/REQ-202608-001

4.2 Issue：維運問題修正

假設維運問題編號為 #105：

git switch dev
git pull origin dev
git switch -c issue/105
git add <修正檔案>
git commit -m "[ISSUE][帳單功能][#105] 修正繳款狀態顯示問題"
git push -u origin issue/105

4.3 Sync：IT 提供程式碼

sync/ 的流程與 feature、issue 相同；差異是製作者與程式碼來源為 IT。同步時保留 IT 提供內容的來源、日期與差異說明。

git switch dev
git pull origin dev
git switch -c sync/20260812-IT-MODIFY
# 放入 IT 提供或調整的程式碼
git diff --check
git diff --stat
git commit -m "[SYNC][程式][IT_MODIFY] 同步 IT 提供程式碼"
git push -u origin sync/20260812-IT-MODIFY
  • 不要把 sync/ 當成 SIT 或 UAT 的替代分支；它仍然是獨立工作分支。
  • IT 提供的程式碼若與目前 dev 有衝突，先釐清保留、合併或回退內容，再進入 SIT。
  • sync/ 完成後，依照 feature / issue 相同方式，個別 merge 到 SIT，再個別 merge 到 UAT。

5. SIT：各工作分支個別整合

SIT 是 HY 測試機上的內部整合區。feature、issue、sync 不必先合成一個暫存分支，而是依照各自的 PR / merge 紀錄個別進入。

5.1 Feature / Issue / Sync 個別進 SIT

以下以 feature 為例；issue 與 sync 只需替換來源 branch 名稱，操作方式相同：

# 將 feature 個別整合進 SIT
git switch SIT
git pull origin SIT
git merge --no-ff origin/feature/REQ-202608-001 -m "[DEV][SIT] Merge feature/REQ-202608-001"
git push origin SIT

# 其他來源也各自執行一次，不是把 SIT 當來源整批搬到 UAT
git merge --no-ff origin/issue/105 -m "[ISSUE][SIT] Merge issue/105"
git push origin SIT
git merge --no-ff origin/sync/20260812-IT-MODIFY -m "[SYNC][SIT] Merge sync/20260812-IT-MODIFY"
git push origin SIT
SIT 的驗收重點每個來源 branch 都要能對應到 PR、需求 / ISSUE / IT 調整說明，以及 SIT 的驗證結果。SIT 可以是多條工作線的整合結果，但每條來源都要可追溯。

6. UAT：各工作分支個別包版

UAT 是包版、差異檔與交付的唯一基準。通過 SIT 驗證的 feature、issue、sync，仍由各自原始 branch 個別 merge 進 UAT；不執行 git merge SIT 作為整批交付方式。

6.1 個別 merge 進 UAT

# 將通過 SIT 驗證的 feature 個別納入 UAT
git switch UAT
git pull origin UAT
git merge --no-ff origin/feature/REQ-202608-001 -m "[DEV][UAT] Merge feature/REQ-202608-001"
git push origin UAT

# issue 與 sync 也各自納入，不從 SIT 整批 merge
git merge --no-ff origin/issue/105 -m "[ISSUE][UAT] Merge issue/105"
git push origin UAT
git merge --no-ff origin/sync/20260812-IT-MODIFY -m "[SYNC][UAT] Merge sync/20260812-IT-MODIFY"
git push origin UAT

6.2 UAT 交付內容

  • 版號 commit 落在 UAT。
  • 包版檔、差異檔、設定異動與交付清單都從 UAT 產出。
  • 若某一條工作分支在 SIT 通過後又被修改，必須重新確認 SIT 驗證結果，再納入 UAT。
  • 交付清單應列出本次 UAT 個別納入的 feature、issue、sync 分支與 commit。

6.3 UAT 交付 Tag

每次完成 UAT 包版、差異檔與交付清單並交付 IT 時，都要在該次實際交付使用的 UAT commit 建立 Tag，命名格式為 UAT/<程式交付日期>。例如：UAT/20260812。同一個 PROD 上線週期若有多次交付，每次都建立新的 UAT Tag，不覆蓋既有 Tag。

# 在實際交付 IT 的 UAT commit 建立 Tag
git switch UAT
git tag -a UAT/20260812 -m "UAT 程式交付 20260812"
git push origin UAT/20260812
禁止作法git switch UAT 後直接執行 git merge origin/SIT，會把 SIT 中不一定要交付的整合內容一併帶入 UAT。

7. main：正式上線紀錄的收斂

UAT 完成包版並由 IT 確認正式環境上線後，才將本次已交付內容收斂回 main。main 的用途是保存 PROD 已確認版本，不拿來做日常開發或暫存整合。

# IT 確認正式環境上線後，依團隊核准方式回併正式紀錄
git switch main
git pull origin main
# 將本次已交付、已確認上線的內容回併 main
git merge --no-ff origin/UAT -m "[SYNC][PROD] 收斂已確認上線版本"
git push origin main

# main 更新後，更新下一輪開發基線
git switch dev
git pull origin dev
git merge --no-ff origin/main -m "[SYNC][BASELINE] 同步 main 至 dev"
git push origin dev

7.1 PROD 上線 Tag

IT 確認正式環境上線並完成 main 收斂後，在代表正式上線版本的 main commit 建立 Tag，命名格式為 PROD/<上線日期>。例如：PROD/20260820。UAT Tag 記錄每次程式交付版本，PROD Tag 記錄最終正式上線版本；一個 PROD Tag 可以對應多個 UAT Tags。

多次交付關係UAT/20260812、UAT/20260814、UAT/20260818 可先後提供給 IT 驗證，最後正式上線後建立 PROD/20260820。交付清單應保留這些 UAT Tag 與 PROD Tag 的對應關係。
# 在正式上線並回併 main 的 commit 建立 Tag
git switch main
git tag -a PROD/20260815 -m "PROD 正式上線 20260815"
git push origin PROD/20260815
版本判斷要交付哪一版，看 UAT；正式上線紀錄，看 main；下一輪開發起點，看 dev。SIT 不扮演 UAT 的來源角色。

8. 特殊情境處理

工作分支可能因為開發時間較長、其他需求先完成上線，導致原本的開發基線已經落後。遇到這類情況時，先確認工作分支與最新 dev 的差異，再決定同步、重開或關閉分支。

共通判斷工作分支進入 SIT 前，必須確認已同步最新 dev 基線；同步後若有程式異動，必須重新完成必要驗證。
閱讀這張圖上方路徑處理已完成的 feature/1～19；下方路徑處理尚未完成的 feature/20。兩條路徑在最新 dev#2 匯合，實際動作是「將 dev#2 merge 進 feature/20」，不是把 feature/20 merge 回 dev#2，也不需要重新逐一 merge feature/1～19。

8.1 工作分支來自舊版 dev

發生情況

feature/20 從 dev#A 建立，但其他工作分支已完成上線，並產生新的 dev#2。

要做什麼

將最新的 dev#2 同步至 feature/20，確認功能可以在最新程式基準上運作。

處理步驟

  1. 確認 feature/20 仍然是有效需求。
  2. 將最新 dev#2 merge 進 feature/20。
  3. 處理衝突並重新測試。
  4. 由 feature/20 個別 merge 進 SIT；SIT 通過後，再個別 merge 進 UAT。

完成判斷：不需要重新 merge 已經進入 main 的 feature；這些內容已透過新的 dev 基線帶入。

8.2 工作分支尚未開始實作

發生情況

分支已建立，但尚未修改程式，或只有少量初始化內容，此時 dev 已經更新。

處理方式

  1. 確認舊分支沒有需要保留的修改。
  2. 從最新 dev 建立新的工作分支。
  3. 註記或關閉原本的舊分支。

完成判斷：後續開發使用最新 dev 作為起點，舊分支不再被使用。

8.3 工作分支已有部分程式

發生情況

工作分支已經有部分開發內容，但需求仍然有效且尚未完成。

處理方式

  1. 保留原工作分支的功能修改。
  2. 將最新 dev merge 進原工作分支。
  3. 處理衝突，確認新基線沒有覆蓋原需求。
  4. 重新編譯、自測，再送 SIT。

完成判斷：原本未完成的功能仍然保留，並能在最新 dev 基線上運作。

8.4 同步最新 dev 時發生衝突

發生情況

兩個需求修改了相同程式區段，將最新 dev merge 回工作分支時發生 conflict。

處理方式

  1. 確認衝突程式分別來自哪一項需求。
  2. 比較兩邊的功能目的與影響範圍。
  3. 由需求或程式負責人確認取捨。
  4. 完成處理後，重新測試受影響功能。

完成判斷：衝突處理結果有人員確認，且 PR 或 merge 紀錄可以追溯決策。

8.5 已進入 SIT 後 dev 又更新

發生情況

工作分支已進入 SIT 並完成部分測試，但 dev 又因其他需求更新。

處理方式

  1. 將最新 dev 同步回工作分支。
  2. 檢查衝突與相依程式異動。
  3. 重新執行受影響測試。
  4. 必要時重新 merge 進 SIT，確認結果後才可進 UAT。

完成判斷：同步後的程式已重新驗證，原 SIT 結果仍適用於目前要交付的版本。

8.6 已交付 UAT 後又需要修改

發生情況

程式已經進入 UAT 並建立 UAT/<程式交付日期> Tag，但測試或 IT 發現需要修正。

處理方式

  1. 保留原本的 UAT Tag，不修改或覆蓋。
  2. 回到原工作分支修正。
  3. 重新完成 code review、測試、SIT 個別 merge 與 UAT 個別 merge。
  4. 重新建立新的 UAT 交付 Tag。

完成判斷：每一次 UAT 交付都有獨立 Tag，可以查出各次交付差異。

8.7 多個 UAT 交付對應一個 PROD

發生情況

同一個正式上線版本可能經過多次 UAT 交付與修正。

處理方式

  1. 每次 UAT 交付都建立新的 UAT/<程式交付日期> Tag。
  2. IT 確認正式上線後，將已確認內容收斂回 main。
  3. 正式上線完成後，在正式上線的 main commit 建立 PROD/<上線日期> Tag。

完成判斷：一個 PROD Tag 可以追溯到該上線週期的多個 UAT Tag，且既有 Tag 不被覆蓋。

8.8 同一天多次 UAT 交付

發生情況

同一天內因修正問題而重複交付 UAT，但日期型 Tag 會產生相同名稱。

處理方式

在團隊規範中加入流水號或時間，避免 Tag 重複，例如 UAT/20260820-01、UAT/20260820-02。

完成判斷：同一天的每次交付都有唯一 Tag，且交付清單能指出實際使用的版本。

8.9 IT sync branch 發生衝突

發生情況

IT 提供的程式碼與目前開發中的程式有差異，不能直接覆蓋其他工作分支。

處理方式

  1. 確認 IT 修改的檔案、原因與來源。
  2. 將 IT 內容保留在獨立的 sync/<日期> branch。
  3. 先釐清保留、合併或回退內容，再個別 merge 進 SIT。
  4. SIT 驗證通過後，再個別 merge 進 UAT。

完成判斷：IT 程式碼有獨立來源紀錄，且沒有直接覆蓋其他需求的工作分支。

8.10 正式環境發生緊急問題

發生情況

正式環境發現問題，但目前 dev 尚有未完成或未驗證功能，不能把整個 dev 帶入正式環境。

處理方式

  1. 以目前正式上線版本，也就是 main 或對應的 PROD Tag，確認問題。
  2. 建立專用的 issue/ 或緊急修正 branch。
  3. 只修改正式問題所需的程式。
  4. 依序完成 SIT、UAT 與正式上線確認。
  5. 正式上線後，將修正內容同步回最新 dev。

完成判斷：正式環境已完成修正，且修正內容已回到開發基線，後續版本不會把修正覆蓋掉。

特殊情境共通原則先確認來源基線，再確認工作分支是否仍需保留；必要時同步最新 dev、處理衝突、重新測試，最後仍由原工作分支個別進入 SIT 與 UAT。

9. Commit、PR 與交付檢查清單

9.1 工作分支 / PR 前

目前在正確的 feature、issue 或 sync branch。
已同步最新 dev，並處理必要衝突。
已執行必要測試、lint 或編譯。
已執行 git diff --check。
沒有把密碼、環境檔或暫存檔帶入 commit。
PR 說明包含目的、變更、測試、風險與回退方式。

9.2 SIT 個別整合前

確認來源 branch 與需求 / ISSUE / IT 調整一致。
每個來源 branch 都有獨立的 merge / PR 紀錄。
合併後記錄 SIT 驗證結果與異常。
SIT 發現問題時，回原工作 branch 修正。

9.3 UAT 個別包版前

只納入已通過 SIT 驗證的工作 branch。
feature、issue、sync 各自 merge 進 UAT。
沒有使用 SIT → UAT 的整批 merge。
版號、包版檔、差異檔與交付清單均以 UAT 產出。
本次每一次交付 IT 的 UAT commit 都已建立獨立的 UAT/<程式交付日期> Tag。
Tag 指向實際交付 IT 的 UAT commit，且沒有覆蓋先前交付 Tag。

9.4 正式上線後

IT 已確認正式環境上線，且已完成本次內容回併 main。
正式上線 commit 已建立 PROD/<上線日期> Tag。
交付清單已記錄多個 UAT Tag 與本次 PROD/<上線日期> Tag 的對應關係。

9.5 Commit 訊息規範與範例

Commit 訊息用來辨識需求開發、Issue 修正、版號更新與 IT 程式同步。開發或修正程式時，Commit 應下在對應的 feature/、issue/ 或 sync/ 工作分支；SIT、UAT 與 main 的 merge 紀錄，請參考前方各環境章節。

Commit 訊息格式[類型][模組（功能）][編號][加註標記] 描述
欄位規則說明
類型DEV、ISSUE、TASK、SYNC依照本次 Commit 的主要目的選擇。
模組（功能）功能名稱、資安、版號或程式填寫實際受影響的功能或程式範圍。
編號依類型使用固定格式DEV 使用 REQ；ISSUE 使用 Issue 編號；TASK 使用 VERSION；SYNC 使用 IT_MODIFY。
加註標記[DB]、[PKG][DB] 表示需提供或執行 SQL Script；[PKG] 表示需安裝或更新第三方套件。同時存在時固定使用 [DB][PKG] 順序。
